# 01 可行性評估

## 結論

**可行。** 規則引擎、牌效計算、點數計算都有成熟的演算法和開源實作可以參考；真正的創新點「可解釋的策略」，做法是把策略寫成人類讀得懂的 if／else 決策函式，並在程式中寫下判斷理由（見 [03](03-strategy-model.md)）。
預期強度大約在中級人類到天鳳上段左右，追不上 Mortal、NAGA 這類價值網路 AI；但本專案的目標本來就是**用強度換取可教學性**。

## 逐項評估

| 目標 | 可行性 | 關鍵 |
|---|---|---|
| 策略編輯 → AI | 高 | 先把框架做對：決策函式依人類思考順序呼叫，並記錄理由 |
| AI 對戰與勝率分析 | 高，但要注意統計 | 必須用 duplicate、大量場次和信賴區間 |
| 練習與復盤 | 中高 | 解釋來自 Trace diff，挑戰在於寫成人話 |
| 讀牌 | 中 | 規則加上統計校準（可用天鳳公開牌譜統計危險度） |
| 詐騙／反詐騙 | 低～中 | 前提是對手有讀牌模型；放到最後做 |

## 主要風險與對策

### 1. 統計雜訊（最容易被低估）
麻將的運氣成分極高。一場半莊的順位標準差約 1.1，要讓平均順位的差距 0.02 達到顯著，**需要上萬場以上**。
- **duplicate**：用同一組 seed 牌山，讓各策略輪流坐每個座位，抵消配牌和摸牌的運氣，通常能少跑好幾倍的場次。
- 報告一律附上 95% 信賴區間；用「兩個相同策略對戰」當 A/A 測試，驗證模擬器沒有偏差。
- 模擬速度是基本需求，這也是選 Rust 的主要原因。目標是單機每分鐘數千場半莊。

### 2. 解釋品質
「分數拆解」不等於「好的解說」。對策是：
- 理由由決策函式直接寫下（`ctx.note`），就是程式實際走過的判斷路徑，不是事後拼湊。
- 只解說貢獻差最大的前 2–3 項，避免資訊過量。
- 可選：把 Trace 交給 LLM 潤飾成自然語言。但數字一律來自 Trace，不讓 LLM 自己推論。

### 3. 手寫判斷的天花板
人工寫的判斷與門檻很快就會遇到瓶頸。對策是兩種獨立的評分：預測用全知視角的準確度評分、決策用反事實模擬評分，讓修改有明確的回饋；M6 再加入具名參數的自動調整，調完依然可以解釋。

### 4. 詐騙的價值
對沒有讀牌的 AI 詐騙毫無作用。要等讀牌（預測）完成，並讓對手 AI 也使用讀牌，才能量測效果。量測不到效果時，可以只保留為「教學說明」用途（解釋迷彩打法的概念）。

### 5. 外部 AI 的授權
Mortal 等專案多為 AGPL，部分權重檔也沒有公開。本專案只透過 **mjai 協定在行程外對接**，不連結或複製它們的程式碼。

## 與現有 AI 的定位

| | 價值網路 AI（Mortal / NAGA） | 本專案 |
|---|---|---|
| 強度 | 極高 | 中上 |
| 輸出 | 各選項的機率或 Q 值 | 決策函式寫下的理由＋各選項的反事實期望值 |
| 可調整 | 需要重新訓練 | 直接修改 if／else 決策程式 |
| 教學 | 「這裡該切 5m」 | 「對手立直、你還差兩步才聽牌，應該棄和；這張是現物，那張只是筋牌而且他用過筋牌騙……」 |

兩者可以互補：在復盤時把強 AI 當作「裁判」，本專案負責解釋（M6/M8，選用）。
